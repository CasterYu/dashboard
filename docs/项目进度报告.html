一、项目目标

面向约 5,000 名用户（封顶 10 万）的只读数据看板，三条核心目标：
  1. 易触达：门店端零安装，浏览器打开网址即看（后续支持企业微信入口）；
  2. 身份校验：登录 + 按角色限定数据范围（总部/大区/小区/门店四级）；
  3. 安全：HTTPS 传输、服务端权限过滤、导入令牌、限流、数据备份。

四、方案取舍（为什么这么选）

4.1 后端：为什么不用 Java + MySQL + Redis 传统三件套

选型只看场景参数：读写比 ≈ 9999:1（全员只读，导入一年几次）、数据量几十万行（整库常驻内存）、维护者 1 人、无专职运维。

（纯只读 + 几十 MB，SQLite/WAL 读性能无差别，且省掉整套数据库运维）（nodesums 物化已把聚合做到毫秒级；真需要时几行 JS 内存缓存即可）（单人维护，Java 分层配置全是税；Express 一个文件看清全部路由）
组件它解决的问题我们是否有此问题
MySQL多服务并发写、数据量超出内存无
Redis数据库查询慢，需前置缓存层无
Spring 全家桶多团队协作的工程化规范无

何时才需要换：多系统写同一数据源、实时流式指标、或团队变成 5 个 Java 工程师——目前无一条成立。届时数据已在 SQLite 中结构化，迁移成本可控。

4.3 其他关键取舍记录

  • 单文件前端 vs 前端工程化（React/Vue + 构建）：选单文件。无 node_modules、无构建链，复制即部署，浏览器双击即用；代价是文件较大（约 190KB），在内部工具场景可接受。
  • mock/api 双模式（v3.8 决策）：前端先于后端迭代，演示/汇报用 mock，生产切 ?data=api，同一套代码两种身份，杜绝"演示版"和"生产版"分叉。
  • 治理先于真实数据（v4.0 决策）：调岗/离职/同名这些"真实数据一导入就爆雷"的问题，提前在演练数据上解决，换来明天导入真实名册时口径不返工。
  • 门店人均积分（v4.1 决策）：排行榜若按门店总积分排名，人多的店天然占优；改人均口径后反映"店里的人干得怎么样"，与绩效诉求对齐。
  • 移动端：新增视图而非重设计（计划 v4.4）：总部分析场景保留桌面；门店"碎片时间扫一眼"场景做独立 mobile.html（本店 KPI + 排行 + 我的积分，登录自动定位），完全复用现有 API，不复制业务逻辑。

五、规模与性能评估（5,000 人 / 封顶 10 万）

场景估算峰值单机承载能力余量
5,000 人早高峰 30 分钟内全部打开30–50 QPSNode + SQLite 只读：数千 QPS（数据常驻内存）充裕
10 万人 1 小时内涌入（极端）≈300 QPS充裕

结论：这是"部署要认真"的量级，不是"架构要重做"的量级。只读 + 数据量小决定了瓶颈不在"多少人看"。到达 10 万用户量级需补齐的仅是部署层：Nginx 静态分流、PM2 多核 cluster、API 短 TTL 缓存、JWT 本地验签。
