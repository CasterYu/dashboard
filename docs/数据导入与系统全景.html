1.1 切换数据源（前端 → 后端）

默认 mock 演示模式（前端内置）。打开 URL 时追加查询参数即可切真实 API：

https://casteryu.github.io/dashboard/?data=api&api=https://api.你的域名.com

前端从 localStorage 读取 JWT（登录后），所有 /api/* 业务请求自动附带 Authorization: Bearer <token>；导入接口仍走 X-Import-Token，与登录体系并存。

1.2 鉴权与会话

  • 5 角色：hq / regional_lead / area_lead / store_lead / employee，scope 按人员当前位置实时计算
  • 登录：POST /api/auth/login { emp_no, password } → { token, user, mustChangePassword }，JWT 有效期 8 小时
  • 首登强改密：返回 mustChangePassword=true 时前端拦截至改密页
  • 导入鉴权：X-Import-Token 头（默认 change-me-import-token，生产必须改）
JWT_SECRET 必须设置：未设置时服务启动会随机生成一次性值并打印警告，重启后所有 token 失效。生产用 JWT_SECRET=$(node -e "console.log(require('crypto').randomBytes(48).toString('hex'))") 生成强随机串并写入 PM2 环境变量。

三、数据导入全景表

本节回答列存储需要几张表、每张表干什么。系统当前共 9 张业务表（不含 meta / import_logs），其中 7 张常态使用、2 张仅在 「灯塔动作积分」模块（v4.6）启用后承载数据。

#表名用途 / 关键字段谁写入谁读取
1org_nodes六级组织树（全国/大区/小区/门店/岗位/人员），parent_id 自指，含 status/deactivated_at/emp_no/store_id/post_keyimport/org全部树形筛选 / scope CTE
2posts10 个岗位配置（积分权重 pw_*），建库时 seed.js 内置seed.js指标导入 / 前端岗位选项
3person_assignments任职记录真源：(person_id, from_date) 唯一，调岗 = 关旧段+开新段import/org历史报表归属回溯
4node_paths物化路径：人员 → 所有祖先，按任职区间分片（from_date/to_date）与上同事务5 角色 scope 子树过滤
5users登录账号：emp_no 唯一 1:1 绑定，password_hash bcryptscripts/create-user.js CLI/api/auth/login
6daily_metrics日指标：(person_id, date) 主键，11 项指标列import/metrics经营总览 / 排行榜 / 漏斗
7action_rules灯塔规则主数据：(post_key, item) 主键，仅 v4.6+ 使用import/rules闭环看板「规则视图」
8action_scores动作明细（每单一笔）：UNIQUE(person, date, item, action, order_no)，仅 v4.6+import/scoring诊断抽屉 AI 时间线
9action_daily_sums个人日汇总：(person, date, item) 主键，达成率直接消费，仅 v4.6+同上事务热力图 / 四象限
辅助表：meta（KV 配置）+ import_logs（每次导入留痕：文件名/模式/行数/失败明细 JSON）→ 通过 /api/import/logs?limit=20 可直接查看。

五、三个导入模板字段

5.1 名册模板 GET /api/import/template?type=org

列名必填说明
大区是如「华东」，不存在则自动建
小区是归属上一级大区
门店是归属上一级小区
岗位是必须命中 posts.key（10 个内置岗位之一）
人员是无工号时需配合门店+姓名唯一定位
工号否强烈建议填，人员唯一身份。命中 → 改名则改名、调岗就切分任职区间；未命中 + 同名 → 「认领」补工号；归属另一姓名 → 视为改名
生效日期否YYYY-MM-DD，调岗/入职时必填，历史报表按当时架构统计
空库开箱可用：建库时已 seed 10 个岗位（含积分权重），「全国」根节点在首次导入时自动创建。旧 5 列名册仍兼容（缺工号的行降级为「岗位/门店+姓名」匹配并单独告警）。

5.2 指标模板 GET /api/import/template?type=metrics

列名必填说明
工号否（强烈建议）填了则优先用工号匹配人员；未填则按姓名+门店/岗位降级
姓名是降级匹配的兜底
日期是YYYY-MM-DD
leads / validLeads / intentLeads / invites / arrivals / testDrives / testReviews / returnVisits / opportunities / locked / delivered 否 11 项指标数值列，缺列默认 0；非数字 → 整行拒绝并返回原因
同人同日覆盖更新，可重复上传；返回 { ok, rowsOk, rowsFailed:[{row, reason}] }，失败行不阻断合法行入库。

5.3 灯塔评分模板 （v4.6+）

上传 Excel 文件，POST /api/import/scoring?postKey=<岗位 key>。两个 sheet：

Sheet 1 · 动作明细

列名必填说明
工号是匹配人员
姓名否冗余便于审计
日期是YYYY-MM-DD
拿分项是必须命中 action_rules.item
动作否如「首访 / 配车 / 交付排程」
订单号否用于诊断抽屉追溯
得分否缺省按规则 per 计算

Sheet 2 · 个人日汇总

列名必填说明
工号是
姓名否
日期是
拿分项是
目标否如 1 / 3 / 5
数量否实际完成数
得分否达成率直接消费
建议先导名册：未覆盖的门店/员工会自动落库（无大区/小区归属，闭环看板分大区树会落到「未归类」节点）。返回 { detailRows, sumRows, persons, storesFromRoster, storesCreatedCount, days }，?dryRun=1 只出报告。

六、导入顺序与依赖

# 4 步流水线（最常跑的路径） [① 名册]── org ──> org_nodes + person_assignments + node_paths │ │ │ ┌───────────────┘ ▼ [② 指标]── metrics ──> daily_metrics ──> 经营总览 / 排行榜 │ │ ▼ [③ 评分]── scoring (v4.6) ──> action_scores + action_daily_sums │ │ │ └─> 热力图 / 四象限 / 诊断抽屉 ▼ [④ 账号 CLI]── create-user.js ──> users（EMP_NULL 与名册 1:1 绑定） # 可独立于名册的导入 [规则]── rules (JSON) ──> action_rules ──> 闭环看板「规则视图」 时机：任何时候，建议首次部署时一次灌入
依赖关系说明
指标 ⇐ 名册指标行必须能匹配到 org_nodes 中的人员节点，否则整行拒绝
评分 ⇐ 名册 + 规则未匹配到人员的工号自动落库（无归属），未匹配到规则项的拿分项拒绝入库
账号 ⇐ 名册账号 emp_no 必须先在 org_nodes.emp_no 存在，否则 CLI 拒绝建号
规则 ⊥ 名册规则是主数据，可独立于名册导入/更新

七、预检与安全阀

7.1 三种导入模式 POST /api/import/org

参数取值行为
modemerge（默认）只新增与调岗，不做离职判定，适合日常增补
snapshot以文件中出现的大区为范围，名单内没有的门店/岗位/人员自动停用，重新出现的自动恢复，未涉及的大区完全不动
dryRun1只返回差异报告（将新增 / 将调岗 / 将停用 / 将恢复 / 已认领 / 失败明细），不写库、不记日志
force1跳过安全阀：停用「人员+门店」数量 > 5 且占比 > 20% 时返回 409 + 待停用清单，人工核对后再加 force=1 重发

7.2 预检示例（PowerShell）

# 全量快照前先预检（不写库） curl.exe -H "X-Import-Token: change-me-import-token" ` -F "file=@名册.xlsx" "http://127.0.0.1:3777/api/import/org?mode=snapshot&dryRun=1" # 确认后正式执行（大批量停用需再带 force=1） curl.exe -H "X-Import-Token: change-me-import-token" ` -F "file=@名册.xlsx" "http://127.0.0.1:3777/api/import/org?mode=snapshot"
软删除 ≠ 物理删除：停用只影响「可见性」，不改变聚合口径。离职人员/闭店门店的历史指标仍完整保留并计入上级合计，因此打开「显示已停用」后榜单求和可能小于上级合计，页面会给出提示语。

八、备份与运维

8.1 每日自动备份

# /etc/cron.d/dashboard-backup 0 2 * * * root sqlite3 /opt/dashboard/server/data/dashboard.db ".backup '/var/backups/dashboard/db-$(date +%F).db'" && find /var/backups/dashboard -name 'db-*.db' -mtime +30 -delete

8.2 升级前备份（跨大版本必做）

pm2 stop dashboard-api sqlite3 /opt/dashboard/server/data/dashboard.db ".backup '/var/backups/dashboard/pre-v4-$(date +%F-%H%M).db'" pm2 start dashboard-api # 启动即自动迁移（幂等）

迁移内容（v4.0 起）：org_nodes 加 status/deactivated_at/emp_no、node_paths 重建为任职区间分片、新建 person_assignments。旧数据回填为「开放区间 + 在职 + 无工号」，升级后数值与旧版逐值一致。

8.3 升级后自检

curl -s localhost:3777/api/health # 应返回 4.6.0 curl -s localhost:3777/api/admin/data-quality | head -c 400 # 工号覆盖率 / 重复工号 / 停用统计 curl -s 'localhost:3777/api/org' | head -c 300 # 组织树（默认已剪掉停用节点）

8.4 物化路径修复

如怀疑「任职区间 → 节点路径」不一致（例如手改过库），可全量重建（幂等，不改变任何聚合数值，仅重建 node_paths 与 node.store_id）：

cd /opt/dashboard/server DATA_DIR=./data node -e "const d=require('./db');console.log(d.rebuildAllPaths(d.openDb()))" # 输出形如 { persons: 8, paths: 54 }
危险操作：node scripts/seed.js --reset 会清空全部数据，生产环境禁用。

8.5 常见运维清单

场景动作
首次上线启动服务 → 下载名册模板 → 填好导入 org → 导入 metrics
月度报表业务侧按模板填 Excel → 导入指标（同人同日覆盖）→ 查看返回失败明细并修正
入职 / 调岗 / 离职 只补新增与调岗 → POST /api/import/org（默认 merge）；调岗建议填「生效日期」，历史报表仍按当时归属。全公司月度对账 → 先 dryRun=1 看差异清单 → mode=snapshot；返回 409 时核对清单后加 force=1
工号治理 GET /api/admin/data-quality 查在职缺工号清单与重复工号；补齐后重导同一份名册即可「认领」（不会产生重复人员）
积分权重调整 改 posts.pw_* 列，历史积分自动按新权重重算，无需回填
升级 git pull && npm install --omit=dev && pm2 restart dashboard-api（跨大版本先按 8.2 备份）
监控 pm2 logs dashboard-api；import_logs 表留全量导入历史；GET /api/import/logs?limit=20 可直接查看
